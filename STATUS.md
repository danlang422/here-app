### Fixed

**`feedback-screenshots` bucket is now private** — Was intentionally public (session 36) so screenshots embed inline in GitHub Issues via `getPublicUrl()`. With the repo now public, the bucket's unauthenticated SELECT policy meant anyone could enumerate and read every screenshot across all orgs via the storage list endpoint — no longer an acceptable tradeoff. `submit-feedback` now uses `createSignedUrl()` (10-year expiry) instead; the bucket has no public/authenticated policies left since all access goes through the edge function's service-role client. See `20260702000001_feedback_screenshots_private_bucket.sql`.

**Six INSERT policy org-scoping gaps closed** — `check_ins`, `presence_waves`, `status_updates`, `post_responses`, `comments`, `notifications` checked row ownership (`student_id`/`author_id = auth.uid()`) but never verified the parent record belonged to the caller's own org — reachable via direct Supabase REST calls with any valid JWT, not through the app's UI. Fixed using the existing `get_my_organization_id()` pattern; `notifications` (no `organization_id` column) checks the recipient via a `user_profiles`-to-`user_profiles` join. See `20260702000002_fix_insert_policy_org_scoping.sql`, session 52.

**`anon` role's inherited table grants revoked** — `anon` held full SELECT/INSERT/UPDATE/DELETE on every pre-existing `public` table (all but `activity_staff`, protected only by having been created later). Root cause: the May 2026 `ALTER DEFAULT PRIVILEGES` migration (`20260513141200`) only governs tables created after it runs, not tables that already existed. RLS was providing real protection throughout (every policy keys off `auth.uid()`/`get_my_organization_id()`, both `NULL` for `anon`), but the grant layer was effectively absent as a second line of defense. Verified no pre-login code path queries `public` schema tables before fixing. See `20260702000003_revoke_anon_inherited_table_grants.sql`, session 52.

**`user_profiles` privilege-escalation gap closed (most significant finding of the ASVS V8 audit)** — the own-row UPDATE RLS policy (`id = auth.uid()`) had no column-level restriction, so any authenticated user could self-assign `roles`, `organization_id`, or `is_active` via a direct REST/PostgREST call — not reachable through the app's own UI, but reachable with nothing more than a valid session token. A student could have granted themselves admin, or moved themselves into a different organization's data. Fixed with a BEFORE UPDATE trigger, `prevent_privileged_self_edit()`, that blocks changes to those three columns unless the acting user already holds `'admin'`. Verified live against real production rows via transactions that ended in `ROLLBACK`: non-admin self-elevation blocked, admin editing another user's role still works, non-admin editing their own non-privileged fields (e.g. `preferred_name`) still works. See `20260714173806_prevent_privileged_self_edit.sql`, session 55.

**`anon` execute grant revoked on two more SECURITY DEFINER helpers** — `get_my_organization_id()` and `activity_is_visible_to_all()` were callable by `anon`, unlike the other three helper functions already restricted to `authenticated`. No actual data exposure (both are scoped to `auth.uid()`, which is `NULL` for `anon`), but it closed a grant-hygiene inconsistency. Found via live grant inspection (Supabase MCP), not migration-file review. See `20260714171604_revoke_anon_execute_org_and_visibility_functions.sql`, session 55.

**`activity_terms` staff-read policy typo fixed** — `activity_terms_staff_select` checked for a `'staff'` role value that has never existed in `user_profiles.roles` (real values: `student`/`teacher`/`admin`) — a leftover typo from the original migration ('teacher' was intended). Dead code, fail-closed (no teacher could read via this policy branch; no security exposure), flagged during session 54's docs pass and fixed during the V8 audit. See `20260714175823_fix_activity_terms_staff_role_typo.sql`, session 55.

**Shared admin-chosen password across all non-admin accounts eliminated (most significant finding of the ASVS V6 audit)** — every non-admin City View account shared one password, set during pre-district-approval test onboarding. Root cause was in two Edge Functions: `reset-passwords` applied one admin-supplied password to every targeted user in the org (a "reset" could only replace one shared password with another), and `create-user` passed an admin-supplied password straight into `auth.admin.createUser()` at account-creation time — found independently during the same session, not part of the original report. Both rewritten to remove admin-chosen passwords entirely: `create-user` now calls `auth.admin.inviteUserByEmail()`; `reset-passwords` now loops `auth.admin.resetPasswordForEmail()` per user. The password field was removed from `UserForm.jsx` and `BulkUserEntry.jsx` — no code path anywhere lets an admin set or know another user's password. The dead `must_change_password` user_metadata flag (never enforced client-side) was removed. Test/dev accounts now use Gmail `+`-alias addresses through the same invite flow as real accounts, rather than a separate weaker path. See commit `87cd3616`, session 56.

**Password policy hardened (6.2.1, 6.2.3, 6.2.5)** — Supabase Auth minimum password length raised to 15 characters (client-side `minLength` in `ResetPassword.jsx`/`Account.jsx` matched); confirmed no character-class composition rule is enabled. Enabled Supabase's "Require current password when changing password" setting and updated `Account.jsx`/`updatePassword()` (`src/api/auth.js`) to collect and send it — verified live that a wrong current password is rejected and a correct one succeeds, and that the post-invite/reset flow (no prior password to check) is unaffected. See commit `29e187c7`, session 56.

**Password-recovery links silently skipping the password-set step, fixed** — Supabase's own dashboard "Send Password Recovery" action has no custom-redirect field, so it lands the user on the project's bare Site URL instead of `/reset-password`. Before the fix, `useAuthListener` treated the resulting session like an ordinary login and `RootRedirect` silently routed the user into their dashboard, skipping the password-set step entirely. Fixed by special-casing the `PASSWORD_RECOVERY` auth event in `useAuthListener` to force navigation to `/reset-password` regardless of landing route (can't apply the same fix to the generic `SIGNED_IN` event without hijacking normal logins — residual gap is procedural: avoid the dashboard's own invite/recovery actions, which only the sole admin can reach anyway). Verified live end-to-end after deploy. See commit `ec2a0e2c`, session 56.

**No working "disable a user" mechanism, fixed (V7 audit)** — `user_profiles.is_active`, the only "disable a user" concept in the codebase, was referenced by zero RLS policies or auth checks — a display/roster filter only, not an authorization gate; no in-app deactivate-user feature existed at all. Fixed by adopting Supabase Auth's native ban mechanism (`auth.users.banned_until`, set via the dashboard's Authentication → Users → Ban action) plus explicit global refresh-token revocation as the actual disable mechanism — deliberately not a custom RLS-based `is_active` check, since most RLS policies check row ownership directly rather than through shared helper functions, making a correct RLS fix mean touching ~20+ individual policies (judged disproportionate for now). Also lowered the project's access-token (JWT) expiry from 3600s to 300s via Project Settings → JWT Keys → Legacy JWT Secret, bounding the residual "already-open session survives the ban" window from up to an hour down to 5 minutes. Verified live via Supabase MCP SQL against a real test account: banned + refresh-revoked → fresh login rejected immediately ("User is banned"), already-open pre-ban session kept working until expiry (expected, per the accepted residual-window design). See `here-security-decisions.md` § Session Management Policy, session 57.

**`user_profiles.roles` had no DB-level CHECK constraint, fixed (V2 audit)** — a full codebase survey (DB CHECK constraints + React Hook Form validation, compiled into the new Input Validation Policy) found `roles` was constrained to `student`/`teacher`/`admin` only client-side, in `BulkUserEntry.jsx`/`UserForm.jsx` — a direct authenticated REST call to PostgREST could have written an arbitrary string into a column that RLS policies and the app's own role-gated routing both read directly. Fixed with `user_profiles_roles_valid CHECK (roles <@ ARRAY['student','teacher','admin'])`. Verified live against production via Supabase MCP: a negative test (INSERT with an invalid role) was rejected citing the constraint by name; the `ALTER TABLE ADD CONSTRAINT` itself validated all existing production rows cleanly as a positive control. See `20260716120000_user_profiles_roles_check.sql`, session 58.

**Recovery/invite links letting a session skip the password-set step entirely, fixed (V2 audit)** — the deeper gap scoped from session 57: a recovery/invite session let a user skip `/reset-password` and land fully authenticated in their dashboard simply by navigating away before submitting a new password, since session 56's fix only did a one-time redirect on the `PASSWORD_RECOVERY` event with no persisted "still owes a password change" state. Daniel manually reproduced this before any fix (clicking a real recovery link, then deleting `/reset-password` from the URL bar, landed cleanly in the dashboard with no password ever set). Fixed with a durable, session-derived gate instead of an event-triggered one: `needsPasswordSetup()` (new `src/lib/authUtils.js`) decodes the session's JWT `amr` claim; `authStore.js`'s `setSession()` derives `passwordSetupPending` fresh on every `getSession()`/`onAuthStateChange` call, not from a one-time flag; `ProtectedRoute.jsx` redirects to `/reset-password` whenever it's true, ahead of role checks, on every render; `ResetPassword.jsx` now signs out after a successful password update, since changing a password isn't itself a new auth event and the gate would otherwise loop forever. Two real bugs were caught by live testing before the fix shipped: an unpadded-base64url JWT decode bug silently made the gate a permanent no-op (caught by Daniel's manual re-test); and Supabase's real `amr` value for both recovery and invite links turned out to be `'otp'`, not the `'recovery'`/`'invite'` values the public docs describe (caught by decoding a real session from a link Daniel provided). Verified with synthetic JWTs injected into localStorage for four scenarios, then end-to-end against a real, previously-unused recovery link for a real test account. Accepted limitation: this is a client-side routing gate, not an RLS-level one — closing that fully would require the same category of schema-wide policy change deferred for `v5.0.0-7.4.2`. See `here-security-decisions.md` § Authentication & Anti-Automation Policy, session 58.
