**Doc-update hook is dry-run only — holding, pending a re-test, not just timing.** `.husky/post-commit` → `scripts/check-docs-updated.sh` fires on every `git commit` (Daniel's or Claude's) and deterministically flags commits that touch substantive paths (`src/**`, `supabase/migrations/**`, `docs/design-and-specs/**`, the ASVS docs) without a paired STATUS.md/session-note update — but it currently only logs to `.git/hook-logs/check-docs-updated.log`, it doesn't launch the headless `doc-updater` run. That's gated behind a local, untracked flag file (`.claude/doc-hook-enabled`, in `.gitignore`) that doesn't exist yet. A controlled live test (session 53.4, isolated to a throwaway git worktree) proved the headless mechanism itself works — but `doc-updater` fabricated a claim in the STATUS.md text it produced (said a flag file existed when it didn't, unprompted). Fixed with a grounding rule added to `doc-updater-agent.md`, but that fix hasn't been re-tested yet. Don't create `.claude/doc-hook-enabled` until it has been. See Next Steps.

### Fixed

**`feedback-screenshots` bucket is now private** — Was intentionally public (session 36) so screenshots embed inline in GitHub Issues via `getPublicUrl()`. With the repo now public, the bucket's unauthenticated SELECT policy meant anyone could enumerate and read every screenshot across all orgs via the storage list endpoint — no longer an acceptable tradeoff. `submit-feedback` now uses `createSignedUrl()` (10-year expiry) instead; the bucket has no public/authenticated policies left since all access goes through the edge function's service-role client. See `20260702000001_feedback_screenshots_private_bucket.sql`.

**Six INSERT policy org-scoping gaps closed** — `check_ins`, `presence_waves`, `status_updates`, `post_responses`, `comments`, `notifications` checked row ownership (`student_id`/`author_id = auth.uid()`) but never verified the parent record belonged to the caller's own org — reachable via direct Supabase REST calls with any valid JWT, not through the app's UI. Fixed using the existing `get_my_organization_id()` pattern; `notifications` (no `organization_id` column) checks the recipient via a `user_profiles`-to-`user_profiles` join. See `20260702000002_fix_insert_policy_org_scoping.sql`, session 52.

**`anon` role's inherited table grants revoked** — `anon` held full SELECT/INSERT/UPDATE/DELETE on every pre-existing `public` table (all but `activity_staff`, protected only by having been created later). Root cause: the May 2026 `ALTER DEFAULT PRIVILEGES` migration (`20260513141200`) only governs tables created after it runs, not tables that already existed. RLS was providing real protection throughout (every policy keys off `auth.uid()`/`get_my_organization_id()`, both `NULL` for `anon`), but the grant layer was effectively absent as a second line of defense. Verified no pre-login code path queries `public` schema tables before fixing. See `20260702000003_revoke_anon_inherited_table_grants.sql`, session 52.

**`user_profiles` privilege-escalation gap closed (most significant finding of the ASVS V8 audit)** — the own-row UPDATE RLS policy (`id = auth.uid()`) had no column-level restriction, so any authenticated user could self-assign `roles`, `organization_id`, or `is_active` via a direct REST/PostgREST call — not reachable through the app's own UI, but reachable with nothing more than a valid session token. A student could have granted themselves admin, or moved themselves into a different organization's data. Fixed with a BEFORE UPDATE trigger, `prevent_privileged_self_edit()`, that blocks changes to those three columns unless the acting user already holds `'admin'`. Verified live against real production rows via transactions that ended in `ROLLBACK`: non-admin self-elevation blocked, admin editing another user's role still works, non-admin editing their own non-privileged fields (e.g. `preferred_name`) still works. See `20260714173806_prevent_privileged_self_edit.sql`, session 55.

**`anon` execute grant revoked on two more SECURITY DEFINER helpers** — `get_my_organization_id()` and `activity_is_visible_to_all()` were callable by `anon`, unlike the other three helper functions already restricted to `authenticated`. No actual data exposure (both are scoped to `auth.uid()`, which is `NULL` for `anon`), but it closed a grant-hygiene inconsistency. Found via live grant inspection (Supabase MCP), not migration-file review. See `20260714171604_revoke_anon_execute_org_and_visibility_functions.sql`, session 55.

**`activity_terms` staff-read policy typo fixed** — `activity_terms_staff_select` checked for a `'staff'` role value that has never existed in `user_profiles.roles` (real values: `student`/`teacher`/`admin`) — a leftover typo from the original migration ('teacher' was intended). Dead code, fail-closed (no teacher could read via this policy branch; no security exposure), flagged during session 54's docs pass and fixed during the V8 audit. See `20260714175823_fix_activity_terms_staff_role_typo.sql`, session 55.
